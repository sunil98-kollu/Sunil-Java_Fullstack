@Configuration
public class RedisConfig {

	@Value("${spring.data.redis.url}")
	private String url;

	@Value("${spring.data.redis.port}")
	private Integer port;

	@Value("${spring.data.redis.username}")
	private String username;

	@Value("${spring.data.redis.password}")
	private String password;

	@Bean
	public JedisConnectionFactory jedisConnFactory() {

		RedisStandaloneConfiguration serverConfig = new RedisStandaloneConfiguration(url, port);

		serverConfig.setUsername(username);
		serverConfig.setPassword(password);

		JedisClientConfiguration clientConfig = JedisClientConfiguration.builder().build();

		return new JedisConnectionFactory(serverConfig, clientConfig);

	}
}

Frequently Asked Scenario Questions
Q1. Why did you use Kafka instead of REST between microservices?

Answer:

Kafka enables asynchronous communication, reduces coupling, improves scalability, and allows multiple consumers (such as Notification, Audit, and Fraud services) to process the same event independently.

Q2. What if a consumer is down?

Messages remain in Kafka (subject to retention settings). When the consumer comes back, it resumes reading from the last committed offset.

Q3. How do you avoid duplicate processing?
Enable idempotent producers where appropriate.
Use unique business transaction IDs.
Make consumers idempotent (safe to process the same event more than once).
Use transactional processing when exactly-once semantics are required.
Q4. How do you preserve message order?

Kafka guarantees ordering within a partition. Use the same message key (for example, accountId) so related events are routed to the same partition.

Q5. How do you handle failed message processing?

Common approaches include:

Retry with backoff
Dead Letter Topic (DLT) for messages that repeatedly fail
Logging and alerting
Manual replay after fixing the issue
